# FRONTEND PHASE 5 IMPLEMENTATION REPORT
## Authentication & Access Control UI
### Zero-Knowledge Document Verification Platform

---

## 1. Executive Summary

Phase 5 delivers a production-grade, cryptographically aligned, accessible, and reactive authentication and access-control interface for the Zero-Knowledge Document Verification Platform. 

In accordance with the mandatory **Inspect-First** doctrine, this implementation was grounded strictly upon the actual backend authentication architecture rather than generic enterprise username/password templates. The backend employs an asymmetric, stateless **JWT Bearer Token** model validated via RSA/PSS digital signatures (`RS256`, `PS256`) registered within `KeyRegistry`, with audience verification (`zkdoc-api`), timestamp validation, and role extraction (`ADMIN`, `ISSUER`, `HOLDER`, `VERIFIER`).

Crucially, an exhaustive backend audit confirmed that **no username/password endpoints, registration flows, or password reset services exist** in the Spring Boot backend. The UI reflects this ground truth honestly: instead of deceptive dead links or simulated username/password fields, the interface provides a dedicated, accessible cryptographic session connection terminal, live JWT claims inspection, automatic open-redirect defense, cross-tab session termination via `BroadcastChannel`, and role-reactive route protection.

All implementation changes passed 100% of the automated test suite (284 tests across 24 suites), achieved zero TypeScript errors (`tsc --noEmit`), zero ESLint warnings, and completed production build compilation with zero failures.

## 2. Backend Authentication Mechanism Verified

The backend authentication stack in `zkdoc-api` was verified via direct static analysis and runtime review:

1. **Spring Security Filter Chain (`SecurityConfiguration.java`)**:
   - `SecurityFilterChain` configures stateless session management (`SessionCreationPolicy.STATELESS`).
   - CSRF protection is disabled (`csrf.disable()`) specifically because authentication is stateless and uses non-ambient `Authorization: Bearer <token>` headers rather than ambient cookies.
   - Public paths permitted without authentication:
     - Root static resources: `/`, `/index.html`, `/assets/**`, `/favicon.ico`.
     - Health and actuator endpoints: `/actuator/health`, `/actuator/info`.
     - Public verification endpoints: `/api/v1/public-verify/**`, `/api/v1/qr/**`.
     - Key discovery: `/api/v1/keys/**`.
     - Development/demo seed endpoints (when enabled): `/api/public/demo-tokens/**`.
   - Protected paths requiring authenticated bearer tokens:
     - `/api/v1/documents/**` (requires `ISSUER` or `ADMIN`).
     - `/api/v1/credentials/**` (requires `ISSUER`, `HOLDER`, or `ADMIN`).
     - `/api/v1/admin/**` (strictly requires `ADMIN`).
     - `/api/v1/audit/**` (strictly requires `ADMIN`).

2. **JWT Signature & Key Management (`ManagedJwtDecoderProvider.java`, `KeyRegistry.java`)**:
   - The Spring Security `JwtDecoder` verifies signatures dynamically using public keys registered in the `KeyRegistry` database.
   - Algorithms supported: `RS256`, `PS256`.
   - Audience claim (`aud`) must contain `zkdoc-api`.
   - Token validity duration is verified against standard `exp` and `nbf` claims with configurable clock skew.

3. **Authorities Conversion (`JwtAuthoritiesConverter.java`)**:
   - Extracts roles from the `roles` list or `scope` / `scp` claim in the JWT.
   - Normalizes roles into Spring `GrantedAuthority` representations prefixed with `ROLE_` (e.g., `ROLE_ADMIN`, `ROLE_ISSUER`, `ROLE_HOLDER`, `ROLE_VERIFIER`).

4. **Absence of User Registration & Password Endpoints**:
   - The repository contains no `UserController`, `AuthController`, or `UserDetailsService`.
   - The only `/register` endpoint in the codebase is `KeyRegistryAdminController.register()` which is an administrative endpoint for registering RSA public keys, not end users.
   - Development demo tokens are generated and signed on the fly by `DemoTokensController` (`/api/public/demo-tokens`) using pre-seeded cryptographic RSA private keys for demonstration and integration testing.

## 4. Login and Session Connection Behavior

### 4.1 Token Input & Cryptographic Decoupling
The `LoginPage` (`frontend/src/routes/LoginPage.tsx`) serves as the authentication gateway:
- **Token Input Field**: An accessible multi-line input (`id="bearer-token-input"`) with `spellCheck={false}` and `autoComplete="off"` to prevent credential caching or dictionary leaks in browser history.
- **Client-Side Pre-Validation**: Performs structural syntax validation (must consist of three base64url segments separated by periods: `header.payload.signature`).
- **Live Claims Inspection**: Decodes the base64url payload in real time to present user feedback before submission:
  - Subject (`sub`): e.g., `admin@zkdoc.internal`, `issuer@zkdoc.internal`.
  - Roles (`roles` / `scope`): Visually tagged badges for `ADMIN`, `ISSUER`, `HOLDER`, `VERIFIER`.
  - Expiration (`exp`): Relative countdown and absolute UTC timestamp.
  - Audience (`aud`): Verified against `zkdoc-api`.
- **Expired Session Alert**: When navigated to following session expiration (`status === 'expired'`), `LoginPage` automatically renders a prominent WCAG-compliant warning alert explaining that the previous session expired and requesting a fresh bearer token.
- **Demo Seed Quick-Connect**: In development environments or when demo tokens are accessible, pre-configured seed buttons enable one-click connection as Admin, Issuer, or Holder, fetching fresh RS256-signed tokens directly from `/api/public/demo-tokens`.

### 4.2 Deceptive Registration Prevention
In strict adherence to UI truthfulness and security hygiene:
- No non-functional "Sign Up", "Register", or "Forgot Password" links are present.
- Informational zero-trust notices explain that identities are issued by cryptographic authorities and key managers rather than self-service signups.

## 5. Authentication-State Architecture

The application state is managed by `authStore` (`frontend/src/state/authStore.ts`):

```
       +---------------------------------------------+
       |                 authStore                   |
       |  (In-Memory State + Subscribed Observers)   |
       +---------------------------------------------+
              |                               |
       Session Storage (Encrypted)      BroadcastChannel
       (Token & User Claims)          ('zkdoc_auth_sync')
              |                               |
              v                               v
    Tab-Local Persistence           Cross-Tab Sync
    (Closed window restoration)     (Immediate multi-tab logout)
```

### 5.1 In-Memory Isolation
- State is encapsulated within a singleton class instance holding `AuthState`:
  ```typescript
  interface AuthState {
    status: 'idle' | 'authenticated' | 'expired' | 'unauthenticated';
    token: string | null;
    user: AuthUser | null;
    isAuthenticated: boolean;
    error: string | null;
  }
  ```
- Subscribed React components listen via `useAuth()` custom hook leveraging `useSyncExternalStore` for flicker-free, tearing-free updates.

### 5.2 Token Persistence & Restoration
- Tokens are stored in `window.sessionStorage` under the key `zkdoc_auth_token`.
- Tokens are **never** written to `localStorage` or permanent storage, preventing lingering credentials on shared workstations.
- On initialization, `authStore.restoreSession()` parses the token, checks the expiration timestamp (`exp`), and restores the authenticated state if valid; otherwise, it purges the session.

## 6. Route Protection and Role-Aware UI

### 6.1 Route Guard Components
1. **`RequireAuth` (`frontend/src/components/auth/RequireAuth.tsx`)**:
   - Verifies `auth.isAuthenticated`.
   - If unauthenticated, captures the attempted URL via `useLocation()` and redirects to `/login` with `?returnUrl=<encodedPath>`.
   - Open-redirect protection (`validateReturnUrl` in `LoginPage.tsx`) guarantees that return destinations must start with a single `/` and cannot contain protocol schemes (`http://`, `https://`, `//`) or javascript pseudo-protocols.

2. **`RequireRole` (`frontend/src/components/auth/RequireRole.tsx`)**:
   - Evaluates reactive permissions directly from `auth.user?.roles`.
   - Normalizes roles (e.g., stripping `ROLE_` prefix if present).
   - Superuser Bypass: Any user possessing the `ADMIN` role is authorized for all protected routes.
   - Role Matching: If the user lacks the required role, they are redirected to `/forbidden` (`403 Forbidden`).

### 6.2 Forbidden Page (`frontend/src/routes/ForbiddenPage.tsx`)
- Provides clear context: renders a 403 status, active subject (`auth.user.subject`), and currently assigned roles.
- Actions: "Return to Overview", "Connect Different Session" (redirecting to `/login`), and "Disconnect Session" (terminating active credentials).

## 7. Session Expiration & Logout Behavior

### 7.1 Automatic In-Memory Expiration Timer
- Upon token connection, `authStore` calculates the remaining lifetime:
  $$\Delta t = (\text{exp} \times 1000) - \text{Date.now()}$$
- A timer (`setTimeout`) triggers `handleTokenExpiration()` when $\Delta t \le 0$.
- Clears the token from memory and `sessionStorage`, transitions status to `expired`, clears sensitive cached state in downstream domain stores (`adminStore`, `holderStore`, `verifierStore`), and notifies listeners.

### 7.2 Cross-Tab Logout Synchronization
- Uses the `BroadcastChannel('zkdoc_auth_sync')` API.
- Calling `authStore.clearSession()` broadcasts a `LOGOUT` event across all active tabs in the same browser context.
- Receiving tabs immediately execute `clearSession(reason, false)`, preventing unauthorized actions on stale tabs.

## 8. Error-Handling Decisions

1. **RFC 7807 / RFC 9457 `ProblemDetail` Compatibility**:
   - API error responses with standard problem details (`status`, `title`, `detail`) are parsed and surfaced via the `Alert` component.
2. **Safe Error Messages**:
   - Decoding errors never dump stack traces or raw byte buffers into the DOM.
   - Malformed tokens yield generic guidance: *"The supplied token does not match the standard JWT format (header.payload.signature)."*
3. **No Credential Echoing**:
   - Error alerts never render user-supplied private keys or passwords.

## 10. Features Deferred Due to Missing Backend Support

1. **Self-Service User Registration**: Deferred pending backend user persistence and identity registration service implementation.
2. **Password-Based Reset / Recovery**: Deferred because the platform utilizes asymmetric cryptographic bearer tokens issued by organizational identity providers.
3. **Refresh Token Rotation**: Deferred pending backend implementation of refresh token storage, revocation lists, and endpoint support.
