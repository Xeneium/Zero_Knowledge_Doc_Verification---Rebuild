## 1. Executive Summary

This integration matrix documents the authoritative contract mapping between the rebuilt React/TypeScript frontend and the Spring Boot backend (`zkdoc-api`). Every frontend route, user action, API client invocation, and data store transition has been reconciled against the authoritative Java `@RestController` definitions, Spring Security filter chains, database persistence entities, and cryptographic validation engines.

All integration points comply with the project's zero-knowledge and minimal-disclosure principles:
- **No Private Keys on Wire:** Frontend strictly enforces public-key-only ingestion for trust anchors.
- **Minimal Disclosure Verification:** Capability verification returns cryptographic validity without exposing document plaintext or holder personally identifiable information (PII).
- **Strict ZKP Payload Boundaries:** Bulletproof range/predicate proof submissions are strictly constrained to mathematical statement fields (`proofVersion`, `credentialId`, `attributeName`, `threshold`, `nonce`, `proofBytes`).
- **Session Teardown & Epoch Isolation:** Cross-session memory wipes and monotonic session epoch guards prevent stale in-flight response leakage across user boundaries.

## 3. Serialization, Header, and Error Contract Guarantees

### 3.1 Traceability Headers
Every request emitted via [`client.ts`](file:///c:/Sabareesh/Easwari%20College/Semester%203/OOPs%20with%20Java/Project/Start%20over/Zero%20Knowledge%20Document%20Verification/frontend/src/api/client.ts) automatically appends:
- `X-Correlation-Id`: Client-generated UUID v4 used by Spring Boot loggers and audit event correlation.
- `Accept`: `application/json` (or `image/png, application/octet-stream, */*` for QR endpoints).
- `Authorization`: `Bearer <jwt>` when authenticated.

### 3.2 Canonical Error Normalization
All backend error envelopes (`ApiErrorResponse`) adhere to Spring's standard error representation:
```typescript
export interface ApiErrorResponse {
  timestamp: string;
  status: number;
  error: string;
  message: string;
  path: string;
  correlationId?: string;
}
```
If an error response arrives as non-JSON (e.g. 502 Bad Gateway HTML page from an upstream proxy), the client constructs an synthetic `ApiError` with HTTP status code and status text, ensuring safe UI presentation without parse exceptions.

## 4. Cross-Workflow Consistency Verification Summary

| Cross-Workflow Scenario | Involved Roles | Frontend Flow | Backend Validation & Storage | Consistency Verification Result |
|---|---|---|---|---|
| **End-to-End Credential Issuance & Verification** | Issuer $\to$ Verifier | Issuer uploads document $\to$ creates Mode B capability $\to$ issues multi-attribute credential | Document hash stored $\to$ signature generated $\to$ capability registered in DB | **PASSED:** Verifier validates capability without document disclosure. |
| **Holder Wallet Provisioning & Predicate Proving** | Issuer $\to$ Holder $\to$ Verifier | Issuer issues credential $\to$ Holder provisions into wallet $\to$ Holder generates Bulletproof proof statement $\to$ Verifier verifies | Ownership verified $\to$ Pedersen commitment created $\to$ Bulletproof verified via `CredentialPredicateController` | **PASSED:** Mathematical proof verified with zero attribute value leakage. |
| **Administrative Lifecycle Oversight** | Issuer $\to$ Admin $\to$ Verifier | Issuer issues active credential $\to$ Admin suspends credential $\to$ Verifier checks validity | Version incremented $\to$ Status updated to `SUSPENDED` $\to$ Verifier rejected with status failure | **PASSED:** Monotonic version bumps and revocation statuses enforced immediately. |
| **Audit Hash-Chain Integrity** | System $\to$ Admin | Actions generate continuous SHA-256 linked audit records | Hash calculated: $H_n = \text{SHA256}(H_{n-1} \parallel \text{payload})$ | **PASSED:** Verified chain across all actions; zero gaps or sequence breaks. |
